AI育儿应用RAG思考与实现

发表于 2026-03-28

从“会聊天”到“可追溯”：Sprout AI 的 RAG 思考与实现复盘

一篇面向真实业务落地的 RAG 实践记录：为什么做、怎么做、做成了什么、还缺什么。

1. 背景：育儿问答为什么必须做 RAG

在育儿场景里，用户最在意三件事：

  • 回答是否可信
  • 建议是否适配宝宝年龄
  • 出问题时是否给出正确风险提示

纯大模型对话可以“说得通”，但不一定“说得准”。
尤其在喂养、发育、发热等高关注问题上，如果没有可追溯的知识来源，产品很难长期稳定。

所以我们在 Sprout AI 里引入 RAG（Retrieval-Augmented Generation）：
把权威知识源、宝宝档案、对话上下文，统一注入到一次生成链路中。

2. 本项目的 RAG 目标定义

我们没有把目标定义成“做一个通用知识库”，而是更聚焦：

  • 场景：0-3 岁 家庭育儿问答
  • 数据源：WHO、CDC、AAP/HealthyChildren、NHS（首批）
  • 输出要求：回答可执行、可解释、可引用
  • 工程要求：失败不阻塞主链路，先保证可用性

一句话：先把“能跑且可信”做对，再追求“更聪明”。

3. 架构总览：离线构建 + 在线检索生成

当前链路分两段：

  1. 离线数据构建
  • import：导入权威知识源
  • chunk：按规则切分知识片段
  • embed：生成向量并写入 pgvector
  1. 在线问答
  • 用户提问 -> 计算 query embedding
  • 向量召回 TopK 片段（带年龄优先）
  • 拼接 RAG 上下文 + 宝宝档案 + 时间上下文
  • 调用模型流式生成
  • 在回复末尾追加“参考来源”

4. 数据层设计：为什么是 Source / Chunk / Embedding 三层

我们在 Prisma 中拆了三张核心表：

  • KnowledgeSource：原始来源与清洗文本（来源、标题、URL、状态等）
  • KnowledgeChunk：切片后的检索单元（topic、ageTag、tags、tokenCount）
  • KnowledgeEmbedding：向量与模型元信息（vector, model, dimensions）

这样的拆分有三个好处：

  • 可追溯：任何回答都能定位到源 URL
  • 可重建：换切块或换 embedding 模型时可局部重跑
  • 可演进：后续加重排、加多向量策略不需要推翻 schema

5. 离线管线实现细节

5.1 Source Import：先做“高质量小规模”

我们没有一上来做全网爬虫，而是把权威内容整理为 Markdown 文件放在 data/rag-sources/。
每个文件用 frontmatter 标注：

  • sourceOrg
  • sourceTitle
  • sourceUrl
  • topic
  • language
  • ageRange
  • status
  • tags
  • publishedAt
  • lastReviewedAt

导入脚本会：

  • 解析 frontmatter
  • 清洗正文（保留段落结构）
  • 按 sourceUrl 做 upsert，保证幂等

这种方式的优点是：前期质量可控，维护成本低，适合业务验证阶段。

5.2 Chunk：可读性优先，不做纯长度盲切

切块策略在 splitIntoChunks 中实现：

  • 先按 Markdown 标题分 section
  • 再合并到目标长度（默认约 600 字符）
  • 最大长度保护（默认约 900）
  • 尾部 overlap（默认约 80）

并为每个 chunk 写入：

  • topic
  • ageTag
  • tags
  • tokenCount（估算）

这一步会先删旧 chunk 和 embedding，再重建，避免脏数据混用。

5.3 Embedding：OpenAI-compatible + pgvector

向量化脚本支持 OpenAI-compatible 接口，默认可用 GLM 路径：

  • EMBEDDING_BASE_URL
  • EMBEDDING_API_KEY / ZAI_API_KEY / GLM_API_KEY
  • EMBEDDING_MODEL
  • EMBEDDING_DIMENSIONS（可选）

实践里有一个工程点：Prisma 对 vector 类型使用 Unsupported("vector")，
所以向量本体通过 SQL 写入（$executeRawUnsafe + ::vector）。

6. 在线检索实现：先把“稳”放在第一位

在线检索由 retrieveKnowledge 完成，流程很直接：

  1. 对用户问题做 embedding
  2. 在 PostgreSQL 中用 ke.vector <=> query 做相似度排序
  3. 以 ageTag 命中优先（例如 6m）
  4. 取 topK=3，并做 minScore 过滤

核心 SQL 思路：

  • score = 1 - distance
  • ageTag 命中排前
  • 再按向量距离升序

这版是“纯向量召回 + 年龄偏置”，还没上 BM25 混合检索和重排器。
优点是链路短、可解释、调参简单。

7. 生成阶段：把 RAG、宝宝档案、时间上下文叠在一起

在聊天流式接口中，我们把上下文分四层注入：

  • 系统规则（安全边界、回答风格）
  • 运行时上下文（当前时间、时区）
  • 个性化上下文（宝宝档案 + 月龄）
  • RAG 检索上下文（TopK 片段）

其中月龄会映射为 ageTag，用于检索阶段优先匹配年龄片段。

一个关键取舍：
RAG 检索失败时不让主链路失败。检索异常会被捕获，模型仍可回退到通用回答。

这保证了服务稳定性，不会因为知识库偶发问题让聊天不可用。

8. “可追溯”是如何落地到用户可见层的

我们做了两层来源透出：

  1. Prompt 层：把检索片段的来源信息（机构、标题、URL）放入 RAG 上下文
  2. 展示层：流式输出结束后，追加“参考来源”Markdown 区块

同时，落库时也会把“回答正文 + 参考来源”一起持久化，
保证历史消息回看时仍然有出处。

这件事非常重要，因为它把“模型说了什么”变成“模型依据什么说”。

9. 这版方案的几个工程取舍

9.1 为什么先不做“全自动爬虫 + 海量知识”

因为早期瓶颈不是“知识太少”，而是“知识质量不稳定”。
先小而精，能更快验证：召回质量是否真的提升了回答可信度。

9.2 为什么先不做混合检索 / 重排

当前体量下，纯向量 + 年龄偏置已经可用。
先把召回、注入、引用、落库这一整条链路走通，比过早堆复杂算法更重要。

9.3 为什么检索失败不抛错

RAG 在业务里是增强层，不应成为单点故障。
用户应该始终得到可用回答，只是“有检索”与“无检索”的质量差异。

10. 已知不足与下一步

当前版本仍有改进空间：

  • 召回层：增加关键词检索与向量混合（Hybrid Search）
  • 精排层：增加 reranker，提升 TopK 质量
  • 评测层：建立离线评估集（命中率、引用正确率、幻觉率）
  • 内容层：补充中文高质量来源与更新策略
  • 安全层：更细粒度的医疗风险策略与拒答策略

我更看重的下一步不是“再加模型”，而是“把评测基线立起来”。

11. 给同类项目的一点建议

如果你也在做垂直场景 RAG，可以直接复用这套节奏：

  1. 先定义“可信来源白名单”
  2. 先把三层数据模型建好（Source/Chunk/Embedding）
  3. 先跑通离线脚本，再接在线生成
  4. 先把“可追溯引用”做出来
  5. 最后再逐步加混合检索与重排

先把“工程闭环”做完，再谈“算法上限”。

12. 文中对应实现位置（便于读者延伸）

  • 数据模型：prisma/schema.prisma
  • 离线脚本：
    • scripts/rag/import-sources.mjs
    • scripts/rag/chunk-sources.mjs
    • scripts/rag/embed-chunks.mjs
  • 在线检索：lib/rag/retrieve.ts
  • 上下文与引用拼装：lib/rag/build-context.ts
  • 聊天接入：app/api/v1/conversations/[conversationId]/messages/stream/route.ts

结语

RAG 在这个项目里，不是“为了用新技术”，而是为了把回答从“看起来合理”推进到“可被信任”。
它本质上是一个产品可信度工程，而不仅仅是模型工程。

一、为什么必须做密码加密？

前端项目中，用户密码若直接明文存储，一旦数据库泄露，会导致用户信息（尤其育儿类产品的儿童隐私数据）泄露。加密的核心目的的是：即使数据库被攻击，黑客也无法获取原始密码，保障用户隐私安全。

核心原则：不存储明文密码，只存储加密后的哈希值，同时通过后端鉴权控制访问权限。

关于React Error Boundary笔记

发表于 2024-04-09

一、Error Boundary 是什么？

Error Boundary（错误边界）是 React 提供的组件级错误处理机制，它是一个只能用类组件实现的特殊组件，专门负责捕获其子组件树中抛出的运行时错误，并阻止错误向上冒泡导致整个应用崩溃，同时显示友好的UI（比如“加载失败，请重试”），而非让页面变成空白。

为什么需要 Error Boundary？

React 组件默认的错误行为是牵一发而动全身：如果某个子组件抛出未捕获的 JavaScript 错误（比如数据格式异常、渲染逻辑错误），整个组件树会被卸载，页面直接变成空白，用户体验极差。

而 Error Boundary 能把错误限制在指定范围，其余组件仍正常渲染。

二、Error Boundary 的核心特性 & 适用范围

1. 能捕获的错误类型

Error Boundary 可以捕获其子组件树中以下场景的错误：

  • 组件渲染过程中的错误（比如 render 方法里的逻辑错误、数据渲染时 undefined.xxx）；
  • 生命周期方法中的错误（比如 componentDidMount 里的异步数据处理错误）；
  • 子组件的构造函数错误。

2. 无法捕获的错误（关键坑点）

Error Boundary 不是万能的，以下错误无法捕获，需用 try/catch 手动处理：

  • 事件处理函数中的错误（比如按钮点击回调、onChange 里的错误）；
  • 异步代码中的错误（比如 setTimeout、fetch/axios 回调、Promise 报错）；
  • Error Boundary 自身抛出的错误；
  • 服务端渲染（SSR）中的错误；
  • 语法错误（比如代码拼写错误，属于编译时错误，运行前就会被发现）。

三、如何实现 Error Boundary（完整示例）

如之前提到的，Error Boundary 必须用类组件实现（React 官方规定），核心是实现两个生命周期方法：

  1. static getDerivedStateFromError：静态方法，捕获错误后更新组件状态，触发降级 UI 渲染；
  2. componentDidCatch：实例方法，捕获错误详情（如错误信息、堆栈），用于日志上报（如 Sentry）。

四、如何使用 Error Boundary

只需把需要保护的组件包裹在 Error Boundary 组件中即可，可灵活控制保护粒度（单个组件/整个页面/整个应用）：

五、总结

  1. Error Boundary ，类组件专属，用于捕获子组件的运行时渲染错误，防止应用整体崩溃；
  2. 捕获错误 → 显示兜底 UI → 记录错误日志，无法捕获事件处理/异步代码中的错误（需 try/catch）；
  3. 按需包裹易出错的组件（如第三方组件、数据渲染组件），粒度不宜过大（比如别用一个 Error Boundary 包裹整个应用，否则一个小错误会让整个应用显示出错UI）；
  4. React 18 提供了实验性的 useErrorBoundary Hook，但未纳入稳定版，生产环境仍推荐类组件实现的 Error Boundary。

React合成事件

发表于 2024-04-03

一、React 合成事件（SyntheticEvent）是什么？

React 合成事件是 React 对浏览器原生 DOM 事件的跨浏览器封装层：

  • 不同浏览器的原生事件（如 click、change）存在兼容差异（比如 IE 的 event 对象获取方式、事件类型命名），React 把这些差异抹平，提供了一套统一、跨浏览器的事件接口；
  • 合成事件模拟了原生事件的所有核心特性（如 target、stopPropagation()、preventDefault()），用法和原生事件几乎一致，但底层做了性能优化（事件委托）和兼容处理。

核心定义：

SyntheticEvent（合成事件）是 React 自定义的事件对象，完全兼容 W3C 标准，封装了浏览器原生事件的行为，同时实现了「事件委托、跨浏览器兼容、性能优化」等特性，是 React 组件事件处理的核心机制。

二、合成事件的核心特性

1. 跨浏览器兼容性

React 替开发者处理了不同浏览器的事件兼容问题，比如：

  • IE 浏览器没有 mouseenter/mouseleave 事件，React 合成事件层模拟了这些事件；
  • 原生事件的 event 对象在不同浏览器中属性不同（如 IE 用 event.srcElement，标准浏览器用 event.target），合成事件统一为 e.target；
  • 无需关注浏览器的事件绑定方式（如 addEventListener vs attachEvent），只需写 React 统一的 onClick/onChange 等。

2. 事件委托

React 不会把事件直接绑定到具体的 DOM 元素上（比如按钮、输入框），而是采用事件委托机制：

  • React 17 之前：所有合成事件都委托到 document 节点上；
  • React 17 及之后：委托到 React 应用的根节点（如 #root），避免和其他第三方库的事件冲突。

为什么这么做？

如果页面有 100 个按钮，每个按钮绑定 onClick，原生方式会创建 100 个事件监听器，占用大量内存；而合成事件只在根节点绑定 1 个监听器，通过事件冒泡找到对应的组件处理函数，大幅减少内存占用，提升性能。

3. 与原生事件高度相似

合成事件对象拥有和原生 Event 对象几乎一样的属性和方法，无需额外学习：

核心属性/方法 作用
e.target 触发事件的原始 DOM 元素
e.currentTarget 绑定事件的组件 DOM 元素
e.stopPropagation() 阻止合成事件的冒泡
e.preventDefault() 阻止事件的默认行为（如 a 标签跳转、表单提交）
e.nativeEvent 指向底层的原生事件对象（可访问原生事件的所有属性）

4. 事件池（React 17 移除）

React 17 之前，为了进一步优化性能，React 会复用合成事件对象：事件处理完成后，会清空合成事件的所有属性，放回事件池供后续复用。

坑点：异步访问合成事件属性会拿到 null，需要调用 e.persist() 保留属性：

React 17 移除了事件池，无需再用 e.persist()，异步访问合成事件属性完全正常。

现代浏览器垃圾回收（GC）效率提升，事件池的性能收益可忽略 。

三、合成事件的工作流程

以点击按钮触发 onClick 为例：

  1. 注册阶段：React 组件声明 onClick={handleClick} 时，React 不会立即绑定到按钮 DOM，而是在根节点注册一个统一的原生 click 监听器；
  2. 触发阶段：用户点击按钮，原生 click 事件冒泡到根节点；
  3. 封装阶段：React 捕获到原生事件，创建对应的合成事件对象（SyntheticEvent）；
  4. 分发阶段：React 根据组件树的层级，找到对应的 handleClick 函数，把合成事件对象传入并执行；
  5. 清理阶段（17 前）：事件处理完成后，清空合成事件对象，放回事件池。

四、合成事件 vs 原生事件

对比维度 React 合成事件 浏览器原生事件
绑定位置 委托到根节点（17+）/document 直接绑定到具体 DOM 元素
兼容性 跨浏览器统一接口 不同浏览器存在差异
事件对象 SyntheticEvent（可访问 nativeEvent） 原生 Event 对象
阻止冒泡 e.stopPropagation() 仅阻止合成事件冒泡，原生冒泡仍会触发 e.stopPropagation() 阻止所有冒泡
性能 事件委托 + 事件池（17前），性能优 每个元素绑定监听器，性能差

五、合成事件的使用注意事项

  1. 不支持部分原生全局事件：如 resize、scroll、load 等全局事件，无法通过合成事件绑定，需手动用 useEffect 绑定到 window/document：
  1. 合成事件的执行时机：React 合成事件在「原生事件冒泡阶段」执行，如需在捕获阶段执行，需给事件名加 Capture 后缀（如 onClickCapture）：
  1. 避免合成事件与原生事件混用：混用容易导致冒泡/执行顺序问题，优先用合成事件，特殊场景（如第三方库）再用原生事件。

总结

  1. React 合成事件是对原生 DOM 事件的跨浏览器封装，核心解决「兼容问题」和「性能问题」；
  2. 事件委托到根节点，减少 DOM 事件监听器数量；
  3. 合成事件的 stopPropagation() 仅阻止 React 内部冒泡，无法阻止原生事件冒泡；
  4. 日常开发优先用合成事件（onClick/onChange 等），全局事件（resize）/第三方库交互场景再用原生事件。

React中调用setState后发生的事情及异步处理机制

发表于 2024-03-22

React中调用setState后发生的事情及异步处理机制

在React中，setState 是用于更新组件状态（state）、触发UI重新渲染的核心API。调用 setState 后并非立即更新state和DOM，而是经过一套「异步调度+批量处理」的流程，其异步机制的核心目的是优化性能、减少不必要的重渲染。以下分两部分详细解析：

一、调用setState后发生的完整流程

无论是类组件还是函数组件（通过useState的更新函数间接调用），调用setState后，React会按以下步骤执行，核心分为「更新入队→批量合并→调度渲染→DOM更新」四个阶段：

1. 接收更新请求，将更新入队

调用 setState(updater, callback) 时，React不会立即修改state，而是先将本次更新请求（可以是对象形式 {key: value} 或函数形式 (prevState) => newState）加入「更新队列」。

这里的关键：更新队列会暂存同一轮事件循环中的所有setState请求，而非立即执行，这是异步处理的基础。

2. 合并更新请求（批量处理）

React会对更新队列中的请求进行「合并优化」—— 若同一轮事件循环中多次调用setState修改同一个state字段，只会保留最后一次的更新，避免多次修改导致的重复渲染。

示例（类组件）：

注：函数形式的setState（setState(prev => prev + 1)）可以避免合并导致的更新丢失，因为它接收的是上一次的最新state，而非当前渲染周期的state。

3. 调度重渲染（异步核心环节）

React会通过「调度器（Scheduler）」判断更新的优先级，将重渲染任务放入「宏任务/微任务队列」，等待主线程空闲时执行（避免阻塞用户交互、滚动等关键操作）。

这里的「异步」并非真正的异步（不是通过setTimeout、Promise实现），而是React内部的「任务调度机制」—— 优先保证主线程的同步操作（如用户输入、事件回调）完成后，再执行重渲染。

4. 执行重渲染，更新DOM

当主线程空闲时，React会从更新队列中取出合并后的更新，修改组件的state，然后触发「 reconciliation（协调）」过程：对比更新前后的虚拟DOM，找出差异（diff算法），只更新需要修改的DOM节点（而非全量更新），最终完成UI渲染。

5. 执行回调函数（可选）

若setState传入了第二个参数（回调函数），则会在DOM更新完成后执行，此时可以获取到最新的state和DOM。

二、setState的异步处理机制（核心解析）

很多开发者会疑惑：「为什么调用setState后，立即打印state得不到最新值？」—— 这正是因为setState的异步处理机制，核心原因的是「React为了性能优化，将更新批量调度，延迟执行」。

1. 为什么setState是异步的？（核心目的）

React设计setState为异步，核心是解决「频繁更新导致的性能问题」：

  • 避免频繁重渲染：若每次调用setState都立即更新state和DOM，当同一事件中多次调用setState（如表单输入、按钮点击），会导致多次重渲染，严重影响性能；
  • 保证UI一致性：异步更新可以确保组件的state和DOM同步更新，避免出现「state已更新但DOM未更新」的中间状态，减少UI错乱；
  • 优先用户交互：将重渲染任务延迟到主线程空闲时执行，避免阻塞用户输入、滚动、点击等关键操作，提升应用流畅度。

2. 异步处理的实现原理

React的异步更新依赖「内部调度机制」和「批量更新策略」，不同React版本（18前后）有细微差异，但核心逻辑一致：

  • React内部维护一个「更新队列」，所有setState请求都会被加入队列，而非立即执行；
  • React会在「当前事件循环的同步代码执行完毕后」，统一处理更新队列中的所有请求，合并后执行一次重渲染；
  • React 18之前：仅在「React合成事件（如onClick、onChange）」和「生命周期函数」中开启批量更新，异步代码（setTimeout、Promise）中不批量更新；
  • React 18之后：开启「自动批处理（Automatic Batching）」，无论在合成事件、异步代码（setTimeout、Promise）中，都能自动合并更新，进一步优化性能。

3. 异步机制的关键误区（必避坑）

误区1：setState是“真正的异步”

错：setState并非通过setTimeout、Promise等异步API实现，而是React内部的「同步入队、延迟执行」。在React合成事件中，setState的更新会被批量延迟，而在原生事件（如addEventListener绑定的事件）、setTimeout中，React 18之前会同步执行更新（18之后仍会批量处理）。

误区2：调用setState后，state一定不会立即更新

错：有两种特殊场景，setState会“同步”更新（React 18之前）：

  • 在原生DOM事件回调中（如document.addEventListener(‘click’, () => { … })）；
  • 在setTimeout、setInterval等异步代码中。

React 18之后，以上场景也会被自动批处理，setState仍为异步。

误区3：可以通过this.state直接获取最新值

错：由于setState是异步的，调用setState后，当前渲染周期的this.state（类组件）或useState返回的state（函数组件）仍然是旧值，只有在重渲染完成后，才能获取到最新值。

正确获取最新值的3种方式：

  1. 使用setState的回调函数（第二个参数）；
  2. 使用函数形式的setState（接收prevState参数）；
  3. 在useEffect（函数组件）或componentDidUpdate（类组件）中获取（监听state变化）。

三、总结

  1. 调用setState后的流程：更新入队 → 合并更新 → 调度重渲染 → DOM更新 → 执行回调；

  2. 异步处理机制核心：React通过「更新队列+批量合并+任务调度」，延迟执行重渲染，避免频繁更新，优先保证用户交互流畅；

  3. 关键注意：setState并非真正的异步，而是React内部的延迟调度；获取最新state需通过回调、函数式setState或生命周期/useEffect；

  4. React 18优化：自动批处理覆盖所有场景，进一步减少重渲染，提升性能。

浏览器的进程模型

什么是进程？

程序运行需要有它自己专属的内存空间，可以把这块内存空间简单的理解为进程

什么是线程？

运行代码的「人」称之为「线程」。

一个进程至少有一个线程，所以在进程开启后会自动创建一个线程来运行代码，该线程称之为主线程。

如果程序需要同时执行多块代码，主线程就会启动更多的线程来执行代码，所以一个进程中可以包含多个线程。

浏览器有哪些进程和线程？

浏览器是一个多进程多线程的应用程序

  1. 浏览器进程
  2. 网络进程
  3. 渲染进程

渲染进程启动后，会开启一个渲染主线程，主线程负责执行 HTML、CSS、JS 代码。

默认情况下，浏览器会为每个标签页开启一个新的渲染进程，以保证不同的标签页之间不相互影响。

渲染主线程是如何工作的？

渲染主线程是浏览器中最繁忙的线程，需要它处理的任务包括但不限于：

  • 解析 HTML
  • 解析 CSS
  • 计算样式
  • 布局
  • 处理图层
  • 每秒把页面画 60 次
  • 执行全局 JS 代码
  • 执行事件处理函数
  • 执行计时器的回调函数
  • ……

什么是异步？

代码在执行过程中，会遇到一些无法立即处理的任务，比如：

  • 计时完成后需要执行的任务 —— <font style="color:rgb(51, 51, 51);background-color:rgb(243, 244, 244);">setTimeout</font>、<font style="color:rgb(51, 51, 51);background-color:rgb(243, 244, 244);">setInterval</font>
  • 网络通信完成后需要执行的任务 – <font style="color:rgb(51, 51, 51);background-color:rgb(243, 244, 244);">XHR</font>、<font style="color:rgb(51, 51, 51);background-color:rgb(243, 244, 244);">Fetch</font>
  • 用户操作后需要执行的任务 – <font style="color:rgb(51, 51, 51);background-color:rgb(243, 244, 244);">addEventListener</font>

如果让渲染主线程等待这些任务的时机达到，就会导致主线程长期处于「阻塞」的状态，从而导致浏览器「卡死」

渲染主线程承担着极其重要的工作，无论如何都不能阻塞！

面试题：如何理解 JS 的异步？

参考答案：

JS是一门单线程的语言，这是因为它运行在浏览器的渲染主线程中，而渲染主线程只有一个。

而渲染主线程承担着诸多的工作，渲染页面、执行 JS 都在其中运行。

如果使用同步的方式，就极有可能导致主线程产生阻塞，从而导致消息队列中的很多其他任务无法得到执行。这样一来，一方面会导致繁忙的主线程白白的消耗时间，另一方面导致页面无法及时更新，给用户造成卡死现象。

所以浏览器采用异步的方式来避免。具体做法是当某些任务发生时，比如计时器、网络、事件监听，主线程将任务交给其他线程去处理，自身立即结束任务的执行，转而执行后续代码。当其他线程完成时，将事先传递的回调函数包装成任务，加入到消息队列的末尾排队，等待主线程调度执行。

在这种异步模式下，浏览器永不阻塞，从而最大限度的保证了单线程的流畅运行。

JS为什么会阻碍渲染?

任务有优先级吗？

任务没有优先级，在消息队列中先进先出

但消息队列是有优先级的

根据 W3C 的最新解释:

  • 每个任务都有一个任务类型，同一个类型的任务必须在一个队列，不同类型的任务可以分属于不同的队列。在一次事件循环中，浏览器可以根据实际情况从不同的队列中取出任务执行。
  • 浏览器必须准备好一个微队列，微队列中的任务优先所有其他任务执行https://html.spec.whatwg.org/multipage/webappapis.html#perform-a-microtask-checkpoint

随着浏览器的复杂度急剧提升，W3C 不再使用宏队列的说法

在目前 chrome 的实现中，至少包含了下面的队列：

  • 延时队列：用于存放计时器到达后的回调任务，优先级「中」
  • 交互队列：用于存放用户操作后产生的事件处理任务，优先级「高」
  • 微队列：用户存放需要最快执行的任务，优先级「最高」

面试题：阐述一下 JS 的事件循环

参考答案：

事件循环又叫做消息循环，是浏览器渲染主线程的工作方式。

在 Chrome 的源码中，它开启一个不会结束的 for 循环，每次循环从消息队列中取出第一个任务执行，而其他线程只需要在合适的时候将任务加入到队列末尾即可。

过去把消息队列简单分为宏队列和微队列，这种说法目前已无法满足复杂的浏览器环境，取而代之的是一种更加灵活多变的处理方式。

根据 W3C 官方的解释，每个任务有不同的类型，同类型的任务必须在同一个队列，不同的任务可以属于不同的队列。不同任务队列有不同的优先级，在一次事件循环中，由浏览器自行决定取哪一个队列的任务。但浏览器必须有一个微队列，微队列的任务一定具有最高的优先级，必须优先调度执行。

面试题：JS 中的计时器能做到精确计时吗？为什么？

参考答案：

不行，因为：

  1. 计算机硬件没有原子钟，无法做到精确计时
  2. 操作系统的计时函数本身就有少量偏差，由于 JS 的计时器最终调用的是操作系统的函数，也就携带了这些偏差
  3. 按照 W3C 的标准，浏览器实现计时器时，如果嵌套层级超过 5 层，则会带有 4 毫秒的最少时间，这样在计时时间少于 4 毫秒时又带来了偏差
  4. 受事件循环的影响，计时器的回调函数只能在主线程空闲时运行，因此又带来了偏差
